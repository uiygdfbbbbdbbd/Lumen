# Decisions

Architecture and product decisions made while building Lumen, newest last. Each entry: what, why, consequences.

## D1. Product name: "Lumen" (configurable)
Placeholder name from the repository. Configurable via `PRODUCT_NAME` env and the admin branding setting
(`branding.productName`), which emails, page titles and the TOTP issuer read at runtime. No third-party marks are used.

## D2. TypeScript 5.9, not 7.0
TypeScript 7 (the native Go port) is the newest release, but typescript-eslint, Vite plugins and drizzle-kit
still target the 5.x API. Pinned `typescript@5.9.3` workspace-wide. Revisit when the ecosystem supports 7.

## D3. Workspace packages consumed from source via a custom export condition
Internal packages export `"@lumen/source": "./src/index.ts"` alongside `dist`. Dev tools (tsx, Vite, Vitest,
`tsc` via `customConditions`) resolve source directly, so there is no rebuild loop in dev. Production builds and
Node at runtime use `dist`. Turbo builds dependencies first (`dependsOn: ["^build"]`).
Caveat: Vitest's `globalSetup` loader does not honour custom conditions, so integration tests need
`packages/*` built first; `turbo run test:int` does this automatically.

## D4. Drizzle ORM + drizzle-kit SQL migrations, with hand-written down files
Forward migrations are generated by drizzle-kit (`apps/server/drizzle/*.sql`) and are the source of truth.
Reversal is supported where feasible via `drizzle/down/<tag>.sql`; `pnpm db:rollback [n]` applies them.
Custom SQL (extensions, triggers) lives in `--custom` migrations.

## D5. Opaque, hashed, rotating session tokens instead of JWTs
Session cookie = 256-bit random token; DB stores an HMAC-SHA256 (keyed with `SESSION_SECRET`). Tokens rotate
after `SESSION_ROTATE_HOURS`; the previous token remains valid for 60 s so parallel in-flight requests are not
logged out (compare-and-swap rotation). Revocation is immediate (no JWT expiry window).

## D6. CSRF: double-submit cookie
`lumen_csrf` (readable, SameSite=Lax) must be echoed in `x-csrf-token` on every cookie-authenticated mutation,
enforced centrally by the `route()` helper. API-key (Bearer) requests are exempt since browsers never attach
them automatically.

## D7. Staff accounts bypass the unverified tier
The first registered user becomes `super_admin`, often before SMTP is configured. Staff roles
(moderator/admin/super_admin) are never placed on the `unverified` tier, otherwise they could not configure email.

## D8. Entitlements are a pure shared function
`computeEntitlements()` in `@lumen/shared` is the only place that decides features/limits. The server enforces
(`route({ feature })`, `EntitlementService.consumeOrThrow`), the client only reads the same result from `/api/me`
to render locks. Precedence: suspended > global kill switch > per-user disable > per-user enable > tier.
Sandbox storage is clamped to a hard 15 GB ceiling regardless of tier or override.

## D9. Quotas are atomic SQL counters
Daily counters live in `usage_counters` and are consumed with a single `UPDATE ... WHERE value + n <= limit`,
which is race-free under concurrency without Redis. Rate limits (short windows) use Redis when configured
(atomic Lua INCR+PEXPIRE) and fall back to an in-memory limiter for single-node/dev/tests.

## D10. Envelope encryption for secrets at rest
AES-256-GCM per value with a random data key, wrapped by a key-encryption key from `ENCRYPTION_KEYS`. Rotation
re-wraps data keys only. Ciphertexts are bound to their owner with associated data (e.g. `totp:<userId>`).

## D11. SSRF guard validates at connect time
`safeFetch` uses an undici Agent whose DNS `lookup` rejects private/reserved addresses, so the address that is
checked is the address that is connected to (defeats DNS rebinding). Redirects are re-validated per hop.
Cloud metadata IPs are blocked even when an admin allows private targets (local Ollama).

## D12. Email testing without Mailpit
This build environment has no Docker daemon, so integration tests capture mail with an in-memory transport
(same render path as production). Docker Compose ships Mailpit for local dev; a Mailpit-backed test variant can
run in CI where Docker exists.

## D13. Integration tests use per-file databases cloned from a template
Global setup migrates + seeds `lumen_it_template`; each test file runs `CREATE DATABASE ... TEMPLATE`, which is
fast and fully isolated. `TEST_DATABASE_URL` points at any Postgres (local, CI service, or Testcontainers).

## D14. Account existence on sign-up
Sign-up returns `EMAIL_TAKEN` for duplicate emails (better UX). Login and password reset never reveal whether an
account exists (same error, constant-time dummy hash, silent reset).

## D15. Coarse location from proxy headers only
No GeoIP database ships with Lumen. When `TRUST_PROXY=true`, country codes are read from CDN headers
(Cloudflare/Vercel/Fastly). Otherwise location is shown as unknown.

## D16. MIT license
Permissive, widely understood, compatible with all dependencies used.

## D17. One OpenAI-compatible adapter for many providers
Mistral, OpenRouter, vLLM, LM Studio and custom endpoints use the OpenAI Chat Completions adapter (with
`max_tokens` instead of `max_completion_tokens`). Anthropic, Gemini, Ollama (native) and Cohere v2 have their own
adapters. All emit one normalized stream (`text-delta`, `reasoning-delta`, `tool-call*`, `usage`, `finish`).

## D18. Token counting is an estimate; billing uses provider-reported usage
Shipping BPE vocabularies would add 1–2 MB per model family. `estimateTokens()` is a calibrated heuristic used
only for context meters and pre-flight checks. Quotas and cost accounting use the usage numbers providers return.

## D19. A built-in mock provider
`@lumen/llm/mock` speaks all five wire formats with deterministic, scriptable behavior. It powers adapter tests,
server integration tests and E2E tests, and lets self-hosters try Lumen without any API key
(`pnpm --filter @lumen/llm mock`).

## D20. Provider keys: many per provider, chosen by weight
Keys live in `provider_keys` (encrypted, bound to the provider with associated data). Selection is weighted random
among enabled keys that are not cooling down (after 429/auth errors) and are under their monthly spend cap.
A per-provider circuit breaker (5 failures, 30 s cooldown, single half-open trial) fails fast during outages.

## D21. PATCH schemas never carry defaults
`.partial()` on Zod objects keeps `.default()` values, which silently reset omitted fields. All PATCH endpoints
use `patchOf(schema)`, which strips defaults and rejects unknown keys. User preferences are merged atomically in
SQL (`jsonb ||`) so concurrent updates to different keys don't overwrite each other.

## D22. Model favorites in the picker use Alt+F
A listbox may only contain options, so the favorite star can't be a nested button. Mouse users click the star;
keyboard and screen-reader users press Alt+F on the active option (shown in the picker's hint line).

## D23. RATE_LIMIT_MULTIPLIER for test environments
All rate limits scale by this env value (default 1). E2E and load tests raise it so a suite of sign-ups from one
IP is not throttled, without weakening production defaults.

## D24. Generations run server-side, decoupled from the HTTP request
`POST /messages` creates placeholders and starts the generation in the background; clients follow
`GET /api/streams/:id` (SSE). Every event gets a sequence number and is buffered in a stream hub (memory, or
Redis Streams when `REDIS_URL` is set), so a client can drop, reconnect with `Last-Event-ID` and resume without
losing or duplicating tokens. Closing the tab does not stop the answer. A heartbeat flush every 1.5 s plus
`recoverStale()` marks generations orphaned by a crash as interrupted.

## D25. Branching is a message tree
Messages have `parentId`; edits and regenerations create siblings; `conversations.active_leaf_id` selects the
visible branch. Compare mode creates 2-4 assistant siblings sharing a `compare_group`; "use this response"
just moves the active leaf. This keeps every version reachable with no data duplication.

## D26. Fallback only before the first token
If the chosen model fails with a retryable error before streaming anything, the admin-configured fallback chain
is tried. Once text has streamed, a failure ends the message with an error (keeping partial text) rather than
splicing in a second model's answer.

## D27. Compaction stores a summary instead of deleting history
When a branch no longer fits the model's context, older turns are summarized by the same model and stored in
`compactions`. The UI shows a marker; the original messages remain visible and searchable.

## D28. Remote images in model output are not auto-loaded
Rendered Markdown shows remote images as labeled links. Auto-loading them would let prompt-injected content
exfiltrate data through image URLs. Raw HTML in model output is never rendered.

## D29. Files are classified by bytes, not by name
Uploads must have an allowlisted extension *and* content that matches it (magic bytes via `file-type`, or valid
UTF-8 for text formats). Mismatches (e.g. a PDF named `.png`, a PNG named `.txt`) are rejected, which blocks
polyglot and renamed-executable tricks. Office/EPUB files are zips and are validated during extraction.

## D30. Hybrid retrieval with reciprocal rank fusion
Each question runs a strict full-text query, a loose OR-of-terms query (stopwords removed) and, when an
embedding model is configured, a pgvector cosine search. Lists are fused with RRF (k=60). Without an embedding
model, retrieval degrades gracefully to lexical search.

## D31. Inline small attachments, retrieve from large ones
If the attachments' total extracted text fits `rag.inlineTokenLimit` (default 8k tokens) it's given to the model
in full; otherwise top-K excerpts are injected with numbered citations and a `file_search` tool is offered.
Users can force either mode per conversation via `PATCH /api/conversations/:id/files`.

## D32. Embedding models are resolved as system models
The admin picks an embedding model in settings. It is used even if it is hidden from the chat model picker
(`enabled = false`), so embedding-only models never show up as chat choices.

## D33. Artifacts run in a sandboxed, network-less runtime frame
HTML and React artifacts run in `/artifact-runtime.html` inside an `<iframe sandbox>` **without**
`allow-same-origin`, so the frame has an opaque origin: no access to app cookies, storage or DOM. Its CSP
(server header and a `<meta>` copy) sets `connect-src 'none'`, so artifact code can't call any network API.
AI and key-value storage go through a postMessage bridge that the parent answers with the viewer's own
session and quotas (`/api/artifacts/:id/ai`, `/storage/:key`), checking `event.source` both ways. The
runtime refuses to run unless it is actually sandboxed (`window.origin === 'null'` and framed), which is why
any site may frame it (`frame-ancestors *`) for embedded public artifacts. `VITE_ARTIFACT_RUNTIME_URL` can
point the frame at a separate origin for extra isolation. React artifacts are compiled in the frame with
sucrase; imports are limited to an allowlist (react, react-dom, recharts, lucide-react).

## D34. Charts are data, drawn by the app
Chart artifacts are JSON (`chartSpecSchema` in shared), never code, and are rendered by an in-app SVG renderer
that follows our dataviz rules: categorical colors come from theme tokens `--lm-chart-1..8` in a fixed order
(separate validated palettes for light and dark), one y-axis only, 2px lines, ≤24px bars with 4px rounded data
ends and 2px surface gaps, a legend for 2+ series, direct end labels only when they don't collide, a
crosshair/per-mark tooltip that also works from the keyboard, and a table view. A "pie" request renders as a
part-to-whole bar (segmented for ≤6 parts, ranked bars beyond) because bars compare parts more accurately;
scatter keeps the first three series (the only slots separable in every pair) and lists the rest in the table.

## D35. Every artifact change is a version
Model edits (`update_artifact` exact replace, `rewrite_artifact`), user edits, spreadsheet cell edits, restores
and undo all append a version (`basedOn` records branching). Restoring or undoing never deletes history. The
code editor is uncontrolled and remounts per version, and warns if the artifact changes while edits are unsaved.

## D36. Self-hosted Monaco, loaded on demand
The source editor is Monaco bundled with its workers (no CDN), in a lazily loaded chunk, so it works offline and
under a strict CSP without affecting the initial bundle (initial JS stays ≈250 KB gz).

## D37. Client-side exports where possible
Source downloads, PNG/SVG (theme variables resolved before rasterizing), CSV (chart data, computed spreadsheet
values) and "PDF (print)" run in the browser. DOCX and PPTX are generated server-side (`docx`, `pptxgenjs`).
LaTeX artifacts are previewed by converting to Markdown + KaTeX; true TeX→PDF compilation needs the Code Mode
sandbox (step 9).

## D38. Gallery thumbnails are live renders
Instead of server screenshots (which need a headless browser), gallery cards render the artifact itself at small
scale once scrolled into view: SVG as an image, charts with the in-app renderer, HTML/React in the same sandbox
without the bridge, text types as an excerpt.
